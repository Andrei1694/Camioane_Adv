# Receiving cards — alarms

Source: [api-181820140.md](../../api/api-181820140.md) - OpenAPI Specification: operation description, request/response schemas and examples. Unversioned API snapshot retrieved 2026-11-10.

**Audience:** Backend, web, mobile. **Use:** Read receiving cards alarms.

## Useful facts

- **`GET /v2/device-status-monitor/receiving-card/alarm/{sn}`** — Read receiving cards alarms.
- Advanced API permission is required. Apply the [Access Guide](doc-4696857.md) authentication and account prerequisites.
- Query by device `sn`; alarm records include source, type/value, hardware position and creation time.
- `level`: `3` risk, `4` fault. `alarmTime` uses the alarm rule’s time zone, which is not necessarily the app user’s zone.
- This is a direct HTTP response, not a push subscription. Monitoring requires VNNOX Care binding; availability depends on the installed device and reporting hardware.
- The source provides no historical time filter, pagination, push callback or acknowledgement workflow. Decode positions using the [location-code notes](doc-4696871.md).

- The schema names the alarm timestamp `alarmTime`, but the example uses `alarmStart`; confirm the wire field.

## App implications and unknowns

Use these alarms for receiving cards diagnostics only when that hardware reports through Care. Confirm alarm freshness, rule time zone and missing-data behavior before showing a resolved/healthy state.
