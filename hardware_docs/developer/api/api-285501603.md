# Scheduled Brightness Adjustment

Source: [api-285501603.md](../../api/api-285501603.md) - OpenAPI Specification: operation description, request/response schemas and examples. Unversioned API snapshot retrieved 2026-11-10.

**Audience:** Backend, web, mobile. **Use:** Schedule fixed or sensor-driven brightness.

## Useful facts

- **`POST /v2/player/scheduled-control/brightness`** — Schedule fixed or sensor-driven brightness.
- Advanced API permission is required. Sub-accounts are limited to their workgroup and its descendants. Apply the [Access Guide](doc-4696857.md) authentication and account prerequisites.
- Maximum 100 players; an empty `schedules` array clears existing brightness schedules. Execution uses player-local time, date bounds and optional weekday filters (empty/omitted means daily).
- Plan `type`: `0` fixed, `1` automatic. Fixed plans require a 0–100 `value`; any automatic plan requires `autoProfile`.
- Automatic profiles map ambient readings to screen brightness (0–100) and require a 0–100 fallback `failValue` when the sensor cannot be read. Segment IDs start at 0 and must be contiguous.
- The source calls ambient units “lumens” and allows 0–65534; other vendor references use illuminance/Lux. Verify units before constructing thresholds.
- Returns `success`/`fail` immediately; no future-execution callback is specified. Detailed plan/profile schemas remain in the source.

- The example uses types `2` and `1`, contradicting the documented `0`/`1` meanings, and uses numbers where segment fields are typed strings. Resolve these conflicts before implementation.

## App implications and unknowns

Expose automatic control only after confirming installed sensors, their units and reporting path. Configure a deliberate fallback and verify schedules in the player’s time zone.
