# Obtaining Player Configuration Status

Source: [api-186309730.md](../../api/api-186309730.md) - OpenAPI Specification: operation description, request/response schemas and examples. Unversioned API snapshot retrieved 2026-11-10.

**Audience:** Backend, web, mobile. **Use:** Read current player settings asynchronously.

## Useful facts

- **`POST /v2/player/current/running-status`** — Read current player settings asynchronously.
- Advanced API permission is required. Sub-accounts are limited to their workgroup and its descendants. Apply the [Access Guide](doc-4696857.md) authentication and account prerequisites.
- Maximum 100 player IDs. `commands` selects volume, brightness, video source, clock/time zone, screen display status, synchronization or multifunction-card power.
- The initial `success`/`fail` lists describe sending. Actual values arrive at required `noticeUrl`; return the literal string `ok` or the service retries.
- Each callback is keyed by `playerId` and `command`. See the named callback schemas for `data`; screen display uses `OPEN`/`CLOSE`, while relay power uses `0` on and `1` off.
- The time callback description incorrectly labels its command `videoSourceValue`, while its example uses `timeValue`. Brightness is typed integer but the example supplies a numeric string.

## App implications and unknowns

Maintain pending state per device/command and handle duplicate callbacks. Confirm the inconsistent payload types/discriminator and retry timing; do not equate requested settings with observed settings.
